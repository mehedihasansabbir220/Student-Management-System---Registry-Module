# v2 Phase 1 — Authentication, Roles & CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the v1 role-toggle cookie with real JWT authentication (rotating refresh tokens, four roles, a permission matrix) enforced on every page and API route, and add a CI workflow. Every existing v1 behaviour and test stays green.

**Architecture:** Pure rules go in `src/domain/permissions.ts` (matrix) and `src/lib/access.ts` (page routing). Crypto primitives go in `src/server/auth/*` (scrypt, opaque tokens) and `src/lib/auth/jwt.ts` (jose, edge-safe so middleware can use it). `src/server/services/auth.ts` owns login, refresh rotation, logout, activation and password change. `src/server/session.ts` exposes `requirePermission` / `requireStudent` guards, which routes call before touching services. Middleware verifies the access JWT for page navigation and bounces expired sessions through `/api/auth/refresh`.

**Tech Stack:** Next.js 15.5 App Router, Prisma 6 / PostgreSQL, zod 4, `jose` 6, `node:crypto` (scrypt, randomBytes, sha256), Vitest 4.

**Spec:** `docs/superpowers/specs/2026-11-27-v2-product-design.md` (§5.1, §5.2, §5.6 "Student account provisioning", §5.7, §5.10 demo protection, §5.11 `ci.yml`, §7 student login policy).

## Global Constraints

- Tests are written **first** and live in `tests/` (`tests/unit` mirrors `src/`, `tests/integration` uses `TEST_DATABASE_URL`). Watch each fail before implementing. Run `npm test`, `npx tsc --noEmit`, `npx eslint .` before every commit.
- Work on branch `v2`. Never `prisma migrate reset`; use `prisma migrate dev --name <x>` locally.
- Verification builds: `NEXT_DIST_DIR=.next-verify npx next build`, server on port 3100. The user's `next dev` owns `.next` on :3000. Don't touch it.
- Roles: `REGISTRY_ADMIN | FINANCE | ACADEMIC | STUDENT`.
- Access token: JWT HS256, **15 min** (`ACCESS_TTL_SECONDS = 900`), `iss: "sms-registry"`, `aud: "sms-web"`, claims `sub, role, sid, studentId?, demo?`. Cookie `sms_at`: httpOnly, SameSite=Lax, Secure in production, Path=/.
- Refresh token: 32 random bytes base64url, **7 days**, cookie `sms_rt`: httpOnly, SameSite=Strict, Path=/api/auth. Only the SHA-256 hex is stored.
- Lockout: **5** consecutive failures → `lockedUntil = now + 15 min`; demo users (`isDemo`) exempt. IP limiter on login: **20 attempts / 15 min / IP**.
- Activation token: 72 h, single use, hashed.
- Passwords: scrypt (`N=16384, r=8, p=1`, 16-byte salt, 64-byte key), format `scrypt$16384$8$1$<saltB64>$<hashB64>`; policy ≥ 10 chars and ≠ email.
- `JWT_SECRET` ≥ 32 chars, validated in `src/server/config.ts` (and in the edge JWT module).
- Error body shape is unchanged: `{ error: { code, message, fields?, requestId } }`. New codes: `TOKEN_EXPIRED` (401), `TOO_MANY_REQUESTS` (429).
- Login failure message is always `"Email or password is incorrect"` (unknown email, wrong password, inactive, not-yet-activated). Locked account: `"Too many failed attempts. Try again in 15 minutes."`
- Audit `actor` format becomes `user:<email>`.
- Never commit `.env`; add every new variable to `.env.example`.

## Review Focus

1. **Two tabs refresh at the same moment** with the same refresh token. Expected: both stay signed in. A presented token revoked **≤ 10 s ago** (`REFRESH_REUSE_GRACE_MS = 10_000`) counts as a benign race: a fresh token is issued in the same family and the family is not revoked. After the grace period it counts as reuse and the family is revoked. → Task 5 tests.
2. **The access token expires mid-form** (user away 20 min, then clicks Save). Expected: `apiFetch` gets `401 TOKEN_EXPIRED`, calls `POST /api/auth/refresh` once, retries the request once and succeeds. If refresh fails, it redirects to `/login?next=<current path>`. → Task 10 tests.
3. **Refresh fails during page navigation** (refresh cookie expired or revoked). Expected: `/api/auth/refresh?next=/staff` clears both cookies and redirects to `/login?next=/staff`, never back to `next`, so there is no redirect loop. → Task 8 test.
4. **Email typed with different case or spaces at login** (`"  Admin@Demo.SMS "`). Expected: it logs in. → Task 5 test.
5. **Tampered, wrong-secret, `alg: none` or expired JWT** in the cookie. Expected: a clean 401 (`UNAUTHENTICATED` or `TOKEN_EXPIRED`), never a 500. Middleware treats it as signed out. → Tasks 3 and 7 tests.
